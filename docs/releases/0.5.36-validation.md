# ClawScribe 0.5.36 Validation Records

Use the published release's `RELEASE-VERIFICATION.json`, installer checksums,
`BUILD-METADATA.txt`, and linked Windows workflow to identify the exact binaries
and checks. A source-version bump or a successful frontend job does not establish
native installer success. Release status is shown in
[GitHub Releases](https://github.com/ch3573r/ClawScribe/releases).

## Evidence Scope

The source preparation passed frontend typechecking and 32 configured helper/control
tests. Isolated Rust module tests passed 43 distinct cases; the provider adapter
was stubbed and these were not whole-application or model-inference tests.

The Windows release pipeline must separately compile the complete application,
build both installers, execute the four required native library test groups, and
verify uploaded asset checksums, build identity, and the NSIS updater signature.
The native helper supplies the staged sherpa/ONNX runtime DLLs to the test binary;
a DLL-loader failure is not a passed test or a compiler assertion failure.

## Prerelease Versus Stable

A prerelease is for manual evaluation and does not advance the stable updater.
It must disclose unconfirmed microphone/system-audio capture, graphical install
and upgrade acceptance, rendered accessibility/scaling, and notebook benchmarks.
Do not treat prompt changes or conservative thread limits as measured accuracy
or performance guarantees.

Stable promotion requires the real-device acceptance described in
[Windows releases](../windows-release.md#required-real-device-acceptance).
Never assert a physical capture test based only on mocks, unit tests, or successful
packaging. The binary commit remains the one recorded in build metadata even if
later documentation commits add clarification.
